# 실행 루프 · 오케스트레이션

## PM 실행 루프

```
Plan      →  작업 분해 + 의사결정 포인트 도출
  ↓
Decide    →  의사결정이 필요한 부분만 사용자에게 질문
  ↓
Execute   →  서브 에이전트 병렬 실행 (독립 작업) 또는 순차 구현
  ↓
Test      →  빌드/테스트 실행 → 통과 확인
  ↓
Report    →  완료 내역 + 다음 단계 간결하게 보고
```

## 서브 에이전트 활용 기준

| 상황 | 활용 방식 |
|------|-----------|
| 독립적인 파일 탐색/분석 | `Explore` 에이전트 병렬 실행 |
| 독립적인 모듈 구현 (예: Entity + Config 동시) | `general-purpose` 에이전트를 worktree 격리 또는 병렬 |
| 설계 방향 검토 | `Plan` 에이전트 |
| 단일 파일 수정 | 메인에서 직접 처리 (에이전트 불필요) |

## 역할 구분

| 역할 | 담당 | 설명 |
|------|------|------|
| PM/오케스트레이터 | Claude (메인) | 계획, 분배, 통합, 보고 |
| 실행자 | Claude (메인 + 서브) | 코드 작성, 테스트, 빌드 |
| 의사결정권자 | 사용자 | 방향 결정, 최종 승인 |

## PM 검증 체크리스트

서브 에이전트 또는 메인에서 작업이 완료될 때마다 아래 항목을 확인한다.

### 1. 정합성 검증
- 코드가 기존 패턴/컨벤션과 일치하는가 (패키지 구조, 네이밍, 응답 래퍼 등)
- `docs/erd.md`, `docs/api-spec.md`와 구현이 일치하는가
- import 누락, 오타, 미사용 코드가 없는가

### 2. 빌드/런타임 검증
- `./gradlew build` 통과 확인 (컴파일 + 테스트)
- 에러 발생 시 **로그 전체를 읽고** 원인을 특정한 후 수정
- 서브 에이전트가 작성한 코드도 **메인에서 빌드 재확인**

### 3. 진행도 추적
- TodoWrite로 완료 항목 즉시 체크
- 일일 계획(`todo/YYMMDD.md`)에 진행 상황 반영
- 세션 보고 시 완료율(%) 포함

### 4. 컨텍스트 비용 감사
- 서브 에이전트에게 **필요한 컨텍스트만** 전달했는가 (전체 코드베이스 탐색 금지)
- 동일 파일을 반복 Read하지 않았는가
- 에이전트 없이 직접 처리할 수 있는 작업에 에이전트를 사용하지 않았는가
- 결과 보고 시 **불필요한 정보 없이 핵심만** 전달했는가

### 5. 디버깅 프로토콜
에러 발생 시 다음 순서를 따른다:
1. **에러 메시지 정독** — 스택트레이스의 원인(Caused by) 확인
2. **관련 파일 1회 읽기** — 해당 라인으로 바로 이동
3. **원인 가설 수립** — "~이 원인일 것이다" 명시
4. **최소 변경으로 수정** — 한 번에 하나만 고침
5. **재빌드로 검증** — 수정 후 즉시 빌드
6. 3회 실패 시 **접근 방식 자체를 재검토**하고 사용자에게 보고

## 실패 대응 원칙

- 에러가 발생하면 **원인 분석을 먼저** 한다. 같은 코드를 반복하지 않는다
- **동일한 접근법으로 3회 이상 실패**하면 접근 방식 자체를 재검토한다
- 막히면 더 작은 단위로 쪼갠다
- 원인을 모르겠으면 솔직히 보고하고 대안을 제시한다
